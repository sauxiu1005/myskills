# 口播文案与用户校对

适用于口播转动画讲解。先判断用户是否提供了本次口播文案，再建立动画和关键词；不能把ASR输出或执行代理自行改写的稿件当成用户已确认文本。

## 缺少文案时的前置步骤

1. **有口播视频/音频、无书面文案**：核听并转写实际讲述，生成可阅读的完整校对稿。恢复标点和段落，核实专名、数字、否定词与代词。以用户提供的背景或可靠语境修正明显识别错误；无法确认的片段单独列出具体疑点，不用猜测填补，也不另写一篇与原声不同的故事。内部保留原始转写和时码，不必把所有时间码堆给用户。
2. **既无文案也无口播音频**：依据已知主题、受众、语言、语气和目标时长生成口播草稿。仅追问实质缺少的主题/事实；普通风格选择可用合理默认。标明时长为估算，未生成音频前不能声称实测。
3. **交给用户校对**：展示完整稿件和少量需要核对的专名/歧义，明确请用户确认或直接修改。将文案状态记为`awaiting_user_review`。文案通过前暂停依赖它的配音、口播视频、付费图片/动画生成及最终烧录合成；可继续源片测量、转写校验、工具确认和可复用的空白版式规划。不要用默认选项、等待超时、旧稿审批或“做完整视频”的笼统授权代替本次缺失文案的确认。
4. **收到回复后**：用户明确通过，或返回修改后的定稿并要求继续时，保存为本次权威文本并记录版本，再测量/校正语义锚点、字幕和关键词。仅返回含疑问的修改建议时继续解决具体疑点，不能直接标为通过。已经确认的同一稿件无需反复审批；用户明确授权跳过校对时遵循其指示并记录。

## 已提供文案与后续校对

- 用户已经提供本次文案时，不再触发“缺文案”确认。以其文本为校对依据，核对拼写、标点、指代、逻辑和实际音频对应关系；用户只要求校对时交付校对稿，不自动生成媒体。用户同时授权制作时，可继续已授权范围内的制作。
- 尽量保留原措辞和语气。分开说明文字纠错与创作改写，未经要求不扩写情节或加入新观点。专有名称按用户原文和可靠语境规范化，例如把误识别的人名校正为“俄耳甫斯”，不要因为ASR给出近音字就把它当成标准拼写。
- 保留原声的项目只修字幕/关键词中的识别错误、标点和明显同音转写，不偷偷改音轨。若用户修改了实质台词而原声未说这些内容，指出差异，请用户决定保留原声还是重录/新配音；不要烧录未说出的整句来假装音画一致。
- 后续提供的权威文案优先于旧的自动转写，更新其所有字幕、关键词、分镜记录和导出依赖。只是文字/标点/专名纠错时，复用已经合格的动画与原声，重做文字图层和合成即可；不重复付费生成素材。

## 制作记录与验收

记录`script_source`（用户原文/源音频转写/新起草）、`script_revision`、`review_status`（draft/awaiting_user_review/confirmed/user_provided）、确认依据、未解决疑点和字幕/关键词所引用的版本。该字段是内部记录约定，不是平台API。

交付前核对：人名/数字/她他/否定词准确，字幕与关键词共同引用最新文本；源声音频的差异已说明；没有把未确认缺文案草稿用于付费生成；没有把旧字幕残留在新版成片。
